# v0.1.0-alpha.6 — experimental preview

Install the CLI from the release tag with [uv](https://docs.astral.sh/uv/):

```sh
uv tool install --python 3.15 "git+https://github.com/franchb/lean-go.git@v0.1.0-alpha.6"
lean-go --version
lean-go doctor
```

The Python package version is `0.1.0a6`. Go library consumers can pin the same
release:

```sh
go get github.com/franchb/lean-go@v0.1.0-alpha.6
```

This preview adds three changes to [alpha.5](v0.1.0-alpha.5.md):

- **Precise compiler-rewrite rejection:** a valid custom `csimp` rewrite now
  produces a structured `admission` / `source_audit` diagnostic, including its
  source owner and location when known. Genuine Lean build failures and invalid
  primitive declarations retain the `build` stage. This refines the diagnostics
  introduced in alpha.5 without admitting custom compiler rewrites.
- **Bitwise extraction:** `UInt32` and `UInt64` each gain AND, OR, XOR, complement
  and logical right shift: ten new audited leaves. Complement stays within its
  operand width; right-shift counts are reduced modulo 32 or 64. Signatures,
  notation support, primitive identities and source closures remain audited.
  See the [bitwise report](../research/extraction-bitwise.md).
- **Standalone proved flags:** the [copyable flag-mask module](../../examples/proofs/flags)
  exposes four `UInt32` roots for setting, clearing, toggling and testing masks.
  Eight universally quantified Lean source claims are checked against separately
  authored expected propositions. Independent Go tests exercise all four roots
  and eight laws over 4,752 input pairs. The module deploys with Go alone.

The compatibility corpus now has 11 cases: five accepted cases, including all ten
bitwise leaves at both widths, and six expected rejections, including valid custom
compiler rewrites. Build failures remain distinct from admission rejections.
The [compatibility harness](../compiler-compatibility.md) is checkout research
tooling, separate from the installed CLI and wheel.

The normalizer, typed APIs, multi-root extraction, quota, reusable proof contracts,
standalone clamp demo and frame-storage reuse remain available. Clamp retains
three source claims and 681 finite Go model pairs; the separate
[release walkthrough](../release-candidate.md) checks a fresh 177-case Go consumer.

## Upgrade from alpha.5

Toolchain pins are unchanged: Go **1.27.4**, Python **3.15** through uv, and
Lean/Lake **4.36.0-rc2** at commit
`b35cb10cf2ced51a2fd1880cfdbf75c71ab7a35a`. The exact Lean commit is required.
The CLI selects its pin without changing Elan's global default.

```sh
uv tool install --force --python 3.15 "git+https://github.com/franchb/lean-go.git@v0.1.0-alpha.6"
lean-go --version
lean-go doctor
```

The module generator is now `lean-go-modulegen/v8`. Schema selection follows
emitted operations, not source spelling or erased uses:

| Emitted program | IR and manifest | Profile |
| --- | --- | --- |
| Existing operations, single root | v6 | `pure-module/v4` |
| Existing operations, multiple roots | v7 | `pure-module/v5` |
| Bitwise operations, single root | v8 | `pure-module/v6` |
| Bitwise operations, multiple roots | v9 | `pure-module/v7` |

Earlier v2–v7 IR retain their primitive restrictions. Single-root packages keep
`Run` / `RunTyped`; multi-root packages keep named typed entrypoints and `RunRoot`.
Resource-limit semantics are unchanged.

Producer and checker inputs have changed since alpha.5. Regenerate package/IR
artifacts and source-proof evidence together, using fresh output paths to inspect
the result; generation preserves and rejects differing existing package bytes.
Pair tagged examples with the CLI from that same tag. Development artifacts need
the CLI from the same checkout, including its local changes.

Packaging still uses Hatchling **1.33.0**. Runtime Python code has no third-party
dependencies; generated consumers need only Go and generated sources with
`CGO_ENABLED=0`.

## Scope and assurance

Width conversions and word packing are outside alpha.6. Division, remainder,
other numeric widths, generic collections, polymorphism, escaping closures,
effects, mutual function recursion, external Lake packages and unsupported
compiler forms remain excluded. APIs and supported compiler forms are experimental.

Lean checks the selected source claims, not an end-to-end compiler-correctness
theorem. Reviewers still judge whether the independently authored propositions
capture the intended requirements. The compiler, extraction adapter, Go emitter
and runtime remain tested and trusted. Finite Go tests and matching hashes provide
regression evidence and traceability, not universal Go proofs or authenticity.
Source elaboration can execute macros and initializers; it is trusted, not
sandboxed. Logical resource budgets can reject an otherwise total Lean call.

## Release validation

Branch checks cover Go tests and vet on Linux and Windows; pinned Lean source
proofs, native comparisons, regeneration, source admission and differential
testing; the same-pin 11-case compatibility corpus; and installed wheel, rebuilt
source-distribution wheel and both standalone demos on Linux and Windows.
The native bitwise suite checks all ten leaves against an independent source model,
native Lean, raw Go and typed Go at 50 input pairs per leaf. The compatibility
bitwise case also covers all ten leaves with an independent Go consumer.

Local candidate tests serve a synthetic module archive through a temporary proxy.
They do not establish public tag availability or the published module checksum.
Exact-tag Go checks download the public release through the Go proxy and checksum
database, verify its version without a local `replace`, and exercise existing
root-module tree, UInt64, quota and multi-root consumers on Linux and Windows.
Those checks alone do not cover every bitwise operation.

The exact-tag installed-CLI workflow separately installs the public Git tag with
uv, checks its package version and toolchain, then freshly generates and verifies
both clamp and flags, including their source proofs and Go-only deployments on
Linux and Windows. The GitHub release record supplies the observed branch and
tag workflow results.
