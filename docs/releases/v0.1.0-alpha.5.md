# v0.1.0-alpha.5 — experimental preview

Install the CLI from the release tag with [uv](https://docs.astral.sh/uv/):

```sh
uv tool install --python 3.15 "git+https://github.com/franchb/lean-go.git@v0.1.0-alpha.5"
lean-go --version
lean-go doctor
```

The Python package version is `0.1.0a5`. Go library consumers can pin the same
release:

```sh
go get github.com/franchb/lean-go@v0.1.0-alpha.5
```

This preview adds three changes to [alpha.4](v0.1.0-alpha.4.md):

- **Lean 4.36.0-rc2:** production extraction requires commit
  `b35cb10cf2ced51a2fd1880cfdbf75c71ab7a35a`. The numeric audit now checks the
  compiler's exact public UInt32/UInt64 order-package declarations. Primitive,
  signature, axiom, source-closure and compiler-replacement checks remain in
  place. The producer still rejects a different version or commit.
- **Structured extraction diagnostics:** `lean-go generate`,
  `scripts/generate.py` and `scripts/export_module.py` provide readable errors
  and optional `--diagnostics=json` reports using `lean-go-diagnostics/v1`.
  Each diagnostic carries a stage and code, the rejection reason, known compiler
  form, original source location and a next-step hint. Unknown fields remain
  null. Source ranges include Unicode, UTF-16 and UTF-8 byte positions; generated
  helpers can identify a validated source owner. The
  [diagnostics guide](../diagnostics.md) defines the schema and process behavior.
  Admission and runtime behavior remain unchanged.
- **Compiler compatibility research:** the Git tag includes
  `scripts/check_compatibility.py` and a nine-case corpus. Runs retain evidence
  and create replay bundles for differences. Four accepted cases cover numeric
  operations, records, helpers and joins; five explicit rejections cover
  polymorphism, externs, unsafe code,
  folded unsupported numeric operations and custom compiler passes. Producer
  build failures are recorded separately and never count as successful admission
  rejections. This is checkout research tooling; it is not an installed CLI
  command and is not bundled in the wheel. See the
  [compatibility guide](../compiler-compatibility.md) for run and replay commands.

The installable CLI, recursive frame-storage reuse, standalone proved-clamp demo,
multi-root extraction, quota library and reusable proof contracts remain
available. The [release walkthrough](../release-candidate.md) checks three clamp
source claims and a separate 177-case Go-only consumer. The
[standalone demo](../../examples/proofs/clamp) retains its 681 finite model cases.
The Apache 2.0 license is unchanged.

## Upgrade from alpha.4

Producers still use Python **3.15** through uv and Go **1.27.4**. Install
Lean/Lake **4.36.0-rc2** from the
[upstream release](https://github.com/leanprover/lean4/releases/tag/v4.36.0-rc2),
or use Elan, then replace the existing CLI:

```sh
elan toolchain install leanprover/lean4:v4.36.0-rc2
uv tool install --force --python 3.15 "git+https://github.com/franchb/lean-go.git@v0.1.0-alpha.5"
lean-go --version
lean-go doctor
```

The CLI selects its exact pin without changing Elan's global default. `doctor`
checks the version and commit, including the Lean executable selected by Lake.
Matching only the version string is insufficient. Alpha.4 remains reproducible
with Lean 4.35.0 at its immutable tag; use that tag's sources and documentation
when checking older artifacts.

Regenerate package/IR artifacts and source-proof evidence together after upgrading.
Compiler and producer/checker inputs have changed, so manifests and evidence from
alpha.4 are not interchangeable with alpha.5. Generation preserves and rejects
differing existing package contents; use fresh output paths to inspect the
regenerated files. The module generator remains `lean-go-modulegen/v7`:
single-root exports retain v6 IR/profile v4 and `Run`/`RunTyped`; multi-root
exports retain v7 IR/profile v5 and named entrypoints. Public APIs and logical
resource-limit semantics are unchanged.

Packaging uses pinned Hatchling **1.33.0**; runtime Python code has no third-party
dependencies. Generated consumers need only Go and generated code, with
`CGO_ENABLED=0`; they need no Lean, Python, uv or C compiler.

## Compatibility and assurance limits

The supported runtime subset remains pure, first-order and monomorphic. General
polymorphism and generic collections remain deferred. External Lake packages,
escaping closures, mutual function recursion, effects, unsupported numeric
operations and unrecognized compiler forms remain unsupported. APIs and
supported compiler forms are experimental.

The compatibility corpus is a small regression experiment, not a proof of compiler
equivalence. Arbitrary later compiler releases require fresh qualification and
review before promotion. A successful research run does not relax the installed
producer's exact version and commit checks.

Lean checks selected source propositions; reviewers decide whether those
propositions capture the intended requirements. The permitted axiom dependencies
remain `propext`, `Classical.choice` and `Quot.sound`. Admitted proofs, custom axioms
and compiler-trust proof shortcuts are rejected. Source-proof evidence and finite
Go tests do not constitute an end-to-end proof of the generated program or a
formally verified compiler. The Lean compiler, extractor, Go emitter/runtime and
Go compiler remain tested and trusted. Hashes provide traceability, not
independent authenticity.

Source elaboration, including macros and initializers, is trusted. Copied
workspaces and process timeouts are not a sandbox for hostile compile-time code.
Generated Go calls can return invalid-limit or exhausted-budget errors; the total
Lean function's theorems do not guarantee success for every operational budget.

## Release validation

Publication requires green branch checks for the tagged commit: Go tests and vet
on Linux and Windows; pinned Lean source proofs, native comparisons, fresh
regeneration, source-admission and differential suites; the complete same-pin
compiler compatibility corpus; and installed-wheel, source-distribution and
standalone-demo checks on Linux and Windows.

Tag checks download the exact public Go version through the module proxy and
checksum database and exercise Go-only consumers on Linux and Windows. The
installed-CLI workflow also installs the exact public Git tag with uv, verifies
its package version, runs `doctor`, regenerates the copied demo, rechecks its
proofs, and runs its Go-only tests and executable on both systems. These checks
are separate from local candidate evidence, whose temporary module archive does
not establish the public module checksum. The GitHub release record links the
observed branch and tag results after they pass.
